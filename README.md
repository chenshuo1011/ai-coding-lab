# 给 AI 一个 118 行的靶子：六种失效模式实测

这个仓库不是教程，是一次对照实验的记录。

起因是一句招聘要求：

> 重度 AI 使用者：日常使用 AI 编程工具，清楚它的边界，知道怎么写问题、怎么验证输出、怎么改错，而不是简单复制粘贴。

这句话没法靠背诵应付。面试官只要追问一句"举个例子"，背的人立刻露馅。所以我需要一个**能反复撞击的小靶子**——足够小，一小时内能改完重跑；足够真实，能暴露真实问题。

靶子最后是一段 118 行的 Word 字数统计脚本（`wordcount.py`）：读 `word/document.xml`，输出总字符数、汉字数；后来加了第四列段落数。AI 助手用 Cline + DeepSeek。

结论先放在前面：**五组实验里只有两组真翻车，而这两组翻的车有共同点——问题都不在代码本身，在它看不见的东西。**

---

## 一、静默失效：教科书写法对某些文档返回 0

我让它用 `python-docx` 重写一份等价实现，本意是抓"编造不存在的 API"。

没抓到。`Document`、`PackageNotFoundError`、`qn`、`element.iter` 全是真的，73 个 docx 逐个对比，两个版本结果完全一致。

于是我读了它的代码，发现第 55 行有一段"第二遍兜底"——它知道 `doc.paragraphs` 不够用，自己补了一遍底层 XML 扫描。把这段去掉，只留教科书写法：

| 文件 | 纯对象模型 | 全 XML |
|---|---|---|
| 博客.docx | 254 / 193 | 254 / 193 |
| 校园报告.docx | 12383 / 9075 | 12383 / 9075 |
| **简历.docx** | **0 / 0** | **1610 / 960** |

那份简历里有 88 个文本框。`doc.paragraphs` 只遍历文档主流程，文本框里的段落不在其中，于是一个字都拿不到。

**它不报错。** 安安静静返回 0，看起来像"这个文件是空的"。如果这是给同学用的工具，同学拿简历一跑，会以为工具把简历弄丢了。

这比"编造 API 后报 AttributeError"危险得多——报错会去查，返回 0 会信。它的代码之所以正确，是因为它踩过这个坑；照教程写的人大概率会踩，而且踩完不自知。

## 二、自证测试：测试全绿，但调用方没接住异常

我让它给脚本写单元测试，然后用变异测试检验这批测试是否有效——把我怀疑的 5 处代码逐一改坏，看测试会不会报警。

5 个变异，全部被杀死。读代码后确认不是巧合：断言写的是字面量（`== (17, 4)`）而不是重算一遍；测了边界的**两侧**（`㐀䶿䷀一鿿𠀀` 六个字符覆盖四个区间端点，连"刚好越界"都测了）；还自己加了 delText 不计入、域代码不计入、嵌套表格不算两遍。

但四天后做边界测试，它崩了：

```
xml.etree.ElementTree.ParseError: unbound prefix: line 1, column 0
```

一份 XML 未闭合的 docx，让整个程序带着 Traceback 退出。原因是 `main()` 只捕获了 `BadZipFile`、`KeyError`、`OSError`，漏了 `ParseError`。

而它的测试里明明有一条 `test_count_docx_malformed_xml_raises_parse_error`——测的是**底层函数会抛异常**，没测**调用方接不接得住**。

> 变异测试只能证明"我改的那几处它能发现"，不能证明"所有地方它都能发现"。手挑的变异恰好落在覆盖范围内，就会给出过度乐观的结论。

上一轮的结论被下一轮的数据修正了。这大概是整件事里最有价值的一次体验。

## 三、边界与修复：1 行改动结束

把报错原样丢回去，我故意没提"记得补测试"，想看它会不会自己想到。

它做对三件事。改动是 1 行：

```diff
-        except (zipfile.BadZipFile, KeyError, OSError):
+        except (zipfile.BadZipFile, KeyError, OSError, ET.ParseError):
```

118 行改完还是 118 行，没有顺手重构。然后主动补了一条测试，测的不是"不崩溃"，而是"坏文件之后还能继续统计后面的好文件"——锁住的是这个 bug 真正伤害的行为。

我把修复撤掉又跑了一遍：31 passed → 1 failed，失败的正是新增那条。**修 bug 的闭环是四步：发现、修复、补测试、验证这条测试真能抓到它。** 少了第四步，下一个人能把它改回去。

## 四、回归：加功能为什么没搞坏旧的

加第四列（段落数）之前，先存档四个文件的基准值。改完再跑，1610 / 960 一个数字没动，测试从 31 条增到 35 条。

关键在实现方式。它没有改 `extract_text()` 的返回值，而是新增内部函数返回元组，旧的保留成一行包装：

```python
def _extract_text_and_paragraphs(xml_bytes):
    return "\n".join(lines), paragraphs

def extract_text(xml_bytes):          # 旧接口原样保留
    return _extract_text_and_paragraphs(xml_bytes)[0]
```

风险从"所有调用方"缩小到"零个调用方"。反过来，如果它直接把返回值改成元组，三十多条测试会当场全挂，而只要它没跑测试，就会以为"改完了，没问题"。

**加功能不破坏旧行为的做法是加一层，不是改原来的。**

## 五、环境盲区：它修对了，但不知道自己对了

把启动脚本里的 python 路径改成一个不存在的路径，双击报错，把报错丢给它。

它没有去改业务代码——这点判断是对的，报错里写的是找不到 `.exe`。但它开始不停生成新文件：`_tmp_a.bat`、`_tmp_b.bat`、`_tmp_strip2.bat`、`_tmp_strip3.bat`、`_dbg.bat`，最后留下六个。看文件名能看出它在做最小复现，方法本身没错。

停不下来的原因在脚本自己身上：`set /p INPUT=` 等输入、`pause` 等按键。AI 的终端没有"人"，命令永远不返回，它收不到输出，判定方案失败，换一个写法，再卡住。

**它没有"这个我测不了"的自觉。** 而产出的那些文件看起来很像在认真干活——判断依据不是"它做了什么"，是"它有没有变得收敛"。

最终版本反而比原来好：绝对路径改成相对路径、加了文件存在检查、空输入不会出错。我实测一遍，1610 / 960，与改前一致。**它修对了，但不知道自己对了。**

## 学到的验收清单

六种里翻车的是第 1、5 条，而它们指向同一件事：**AI 的可靠性缺口集中在它看不见的地方**——你的环境、你的真实文档、你代码的调用方。代码本身，它已经相当可靠。

留下来的规则，都是可执行的：

- **给它跑的脚本不能有 `input()`、`pause`、`set /p`。** 一切等人工输入的交互，都会在它那里死锁。
- **测断言看右边。** 写死的数字是真的测；又调一次被测函数来算期望值，是自证。
- **换一个奇怪的文件再跑一次。** 不是"跑通了就算"，是"拿它没见过的东西跑一遍"。
- **改代码前先记数字。** 没有基准就没有回归，事后补记不算。
- **测试全绿不等于没漏洞。** 想知道测试有没有用，把代码故意改坏，看它挂不挂。

工具都在这个仓库里：`mutation_test.py` 是那个"改坏代码看测试报不报警"的小工具，`实验手册.md` 是完整记录，含每次实验的原始输出和当时的判断过程。`edge_cases/` 里是四个故意造的坏文件。

`wordcount.py` 与测试是从 `tools/` 拷来的快照，方便对照阅读。

如果只记一句：**"能跑通"和"写对了"之间，隔着一批你不会想到要测的输入。**
